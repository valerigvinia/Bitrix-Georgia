## 1. მიზანი და მომხმარებლის გზა

საიტმა უნდა უპასუხოს: რა არის Bitrix24; რას აკეთებს Bitrix Georgia; რომელი სერვისი მჭირდება; როგორ განისაზღვრება ლიცენზიისა და მომსახურების ფასი; როგორ მოვითხოვო კონსულტაცია.

სამი ძირითადი გზა:
1. CRM-ს პირველად ეცნობა → Bitrix24-ის შესაძლებლობები → შესაბამისი სერვისი → კონსულტაცია.

3. ეძებს ტარიფს → ყოველთვიური/წლიური შედარება → ტარიფის არჩევა → შეთავაზების მოთხოვნა არჩეული ტარიფით.

სტატია → დაკავშირებული სერვისი → კონსულტაცია არის მეოთხე, ინფორმაციული გზა. მთავარ გვერდზე ყველა თემის სრულად ჩატევა საჭირო არ არის; მან შესაბამის გვერდზე უნდა გადაიყვანოს მკითხველი.

## 6. სიახლეების განყოფილება

საჯარო სახელწოდება: **„სიახლეები და სტატიები“**; header-ში მოკლედ „სიახლეები“.
კატეგორიები: Bitrix24-ის სიახლეები; პრაქტიკული გზამკვლევები; კომპანიის ამბები. „CRM სისტემა ქართულ ბიზნესში“ მიეკუთვნება გზამკვლევებს და არა ახლად გამოქვეყნებულ ამბავს.

არქივი: მოკლე სათაური/აღწერა → კატეგორიების ფილტრი → საძიებო ველი → ბარათები (cover, კატეგორია, თარიღი, სათაური, ანონსი) → pagination. ფილტრებისა და ძიების მდგომარეობა აისახება URL-ში. featured ბლოკი მხოლოდ რედაქტორის მონიშვნისას. შედეგის არქონისას გასაგები შეტყობინება და ფილტრების გასუფთავება.

სტატია: breadcrumb, სათაური, ანონსი, ავტორი, გამოქვეყნების თარიღი; განახლების თარიღი მხოლოდ რეალური ცვლილებისას; cover/alt, სტრუქტურირებული ტექსტი; გრძელი სტატიისთვის სარჩევი; წყაროს ბმულები; დაკავშირებული მასალა და სერვისის CTA. უცნობ slug-ზე 404.

კონტენტის მოდელი:
- id, slug, title, excerpt, body, category;
- coverImage, imageAlt, author;
- publishedAt, updatedAt, status (draft/published), featured;
- seoTitle, seoDescription, sourceUrl საჭიროებისას;
- relatedServiceSlugs, legacyUrl.

სამუშაო ნაკადი: მონახაზი → რედაქტირება/ფაქტების გადამოწმება → preview → გამოქვეყნება → არქივისა და მთავარი გვერდის განახლება. მომავლის თარიღიანი და draft ჩანაწერები საჯაროდ არ გამოჩნდება. რეალური ავტორის/თარიღის არქონისას მონაცემები არ მოიგონება.

CMS არჩევანი დადასტურებულია მომხმარებლის მიერ: **არსებული WordPress ადმინისტრაცია + Next.js საჯარო საიტი**. მომხმარებელი ნაცნობ WordPress-ში წერს, არედაქტირებს და აქვეყნებს; Next.js REST API-ით იღებს გამოქვეყნებულ სტატიებს და საკუთარი დიზაინით აჩვენებს. Article მოდელი იქნება საერთო კონტრაქტი WordPress-სა და UI-ს შორის. WordPress-ის ჰოსტინგი რჩება საჭირო; მხოლოდ ვებსაიტის საჯარო ნაწილი გადადის Vercel-ზე.

დაკავშირების კონკრეტული გეგმა:
1. ახლა read-only წყაროა `https://bitrixgeorgia.ge/wp-json/wp/v2/posts`; გადაამოწმდეს კატეგორიები, მედია, ავტორები და pagination. საჯარო API ამ ეტაპზე ხელმისაწვდომია.
2. Next.js-ს ჰქონდეს სერვერული `WORDPRESS_API_BASE_URL` და წყაროზე ერთი adapter. არც ერთ კომპონენტში არ ჩაიწეროს ძველი დომენი ხისტად.
3. გამოქვეყნების/განახლების/წაშლის შემდეგ WordPress აგზავნის დაცულ webhook-ს; Next.js ასუფთავებს არქივის, სტატიისა და მთავარი გვერდის cache-ს. დამატებით შეთანხმებული დროითი revalidation, თუ webhook ვერ მოვიდა. მიღების სამიზნე: გამოქვეყნებული ცვლილება საიტზე ჩანს მაქსიმუმ 5 წუთში, ნორმალური ხელმისაწვდომობის პირობებში.
4. draft preview საჭიროებისას იყენებს სერვერულ ავტორიზაციას და შეზღუდულ preview ბმულს; მონახაზები საჯარო API-ს გზით არ ქვეყნდება. რეალური გასაღებები მოგვიანებით ჩაიწერება სერვერულ გარემოში.
5. დომენის გადართვამდე მომზადდეს WordPress-ის ცალკე მისამართი, მაგალითად `cms.bitrixgeorgia.ge` (ჯერ მხოლოდ წინადადებაა, DNS-ის შეცვლის ნებართვა არ გაცემულა). გადაიხედოს WordPress URL-ები, media ბმულები, REST, webhook, login და სარეზერვო ასლი.
6. ახალი frontend-ის მთავარ დომენზე გადაყვანის შემდეგ API მაინც WordPress-ის სწორ ჰოსტს უნდა მიმართავდეს. ეს შემოწმება აუცილებელია, რადგან ძველი `bitrixgeorgia.ge/wp-json` Vercel-ზე გადასვლისას თავისთავად აღარ იქნება WordPress.
7. სტატიის canonical ახალ საჯარო `/news/[slug]` გვერდზე მიუთითებს. CMS-ის საჯარო HTML არქივები არ უნდა გახდეს ინდექსირებადი დუბლიკატები; REST/მედიის წვდომა შენარჩუნდება.

ტექნიკური წყაროები: https://developer.wordpress.org/rest-api/reference/posts/ და https://nextjs.org/docs/app/api-reference/functions/revalidateTag . კონკრეტული caching API-ის გამოყენება გადამოწმდება პროექტში დაყენებული Next.js ვერსიის მიხედვით.

საჯარო WordPress HTML პირდაპირ არ ჩაისმება შემოწმების გარეშე: საჭიროა უსაფრთხო ბლოკებად გარდაქმნა/სანიტიზაცია, მედიის სწორი URL-ები და შიდა ბმულების გადაწერა. CMS-ის განახლება გაასუფთავებს შესაბამის cache-ს ხელმოწერილი webhook-ით ან შეთანხმებული პერიოდული განახლებით. წყაროს გათიშვისას გამოჩნდება ბოლო წარმატებული გამოქვეყნებული მასალა; პირველი ჩატვირთვის სრული ჩავარდნა გამოჩნდება შეცდომად, არა ცარიელ წარმატებულ არქივად.

სიახლეები პირველი სრული გამოშვების ნაწილია და არ გადაიდება განუსაზღვრელ „მომავალ ეტაპზე“.

გამოშვების შემოწმება:
- ყველა 16 ძირითადი მარშრუტი და ერთი რეალური სტატია იხსნება; უცნობი სერვისი/სტატია აბრუნებს 404-ს.
- მენიუ მუშაობს keyboard/touch-ით; focus ხილულია; პატარა ეკრანზე ჰორიზონტალური scroll არ ჩნდება.
- შემოწმებულია მინიმუმ 360/390, 768 და 1440 px სიგანეები; კონტრასტი და ველების label/error კავშირები.
- სიახლეების ძიება, კატეგორია, pagination, ცარიელი შედეგი, draft-ის დამალვა და გამოქვეყნების შემდეგ განახლება მუშაობს.
- ფასების ორივე პერიოდი, ვალუტა, მოძველება და შეცდომა სწორად ჩანს; პირობითი თანხები არ გამოიყურება ოფიციალურად.
- მოთხოვნის მიღება დადასტურებულია CRM-ში/მიმღებთან; განმეორებითი/შეცდომიანი გაგზავნა მართვადია.
- გამოსახულებები შესაბამისი ზომისაა; მედიას აქვს alt; გვერდებს მეტამონაცემები და სწორი canonical.
- 301 რუკა, sitemap, robots, production ინდექსაცია შემოწმებულია დომენის გადართვისას.
- `npm run build`, `npm run typecheck`, შესაბამისი ფუნქციური შემოწმებები და Vercel READY.

## 11. საჭირო მასალა და ღია გადაწყვეტილებები

მფლობელისგან: ფერადი ვიზუალური მიმართულების თანხმობა; საბოლოო ლოგოს კარგი ხარისხის წყარო თუ ხელმისაწვდომია; რეალური კომპანიის/გუნდის ტექსტი; შეთავაზებული ექვსი სერვისის ბიზნესთან შესაბამისობა; ლიდების მიმღები; პარტნიორის სტატუსის მტკიცებულება თუ გამოიყენება. სიახლეების ადმინისტრირება უკვე გადაწყვეტილია: WordPress.

ჯერ საჭიროა ამ გეგმისა და ფერადი დიზაინის კონკრეტული შაბლონების განხილვა. არსებული ბრენდბუქის განახლება ცალკე ნებართვით მოხდება; მის დასამტკიცებლად საკმარისი არ არის ზოგადი მითითება „საიტი გააუმჯობესე“.
